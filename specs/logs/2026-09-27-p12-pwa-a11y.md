# 2026-09-27 — P12 PWA + a11y polish

## What shipped

**PWA**: `vite-plugin-pwa` (already a dependency, previously unwired) is now registered in `apps/web/vite.config.ts` (`registerType: 'autoUpdate'`, workbox precaching of the built app shell). A real web manifest (`name`, Hindi-first `description`, `theme_color`/`background_color` matching the brand purple, `display: standalone`, `lang: hi`) is generated by the plugin. A real icon set (`pwa-192x192.png`, `pwa-512x512.png`, `pwa-maskable-512x512.png`, `apple-touch-icon.png`) was rasterized from the existing `favicon.svg` mark. `index.html` got `<link rel="apple-touch-icon">` and `<meta name="theme-color">` (the manifest link and SW register script are auto-injected by the plugin at build time). `.gitignore` now ignores `dev-dist` (the plugin's dev-mode output — previously only oxlint-ignored, not git-ignored).

**A11y**: enabled oxlint's built-in `jsx-a11y` plugin. Fixed the two real findings (`autoFocus` on the phone/OTP inputs in `LoginScreen.tsx` — removed, since stealing focus before the screen title is read is a real regression risk for a voice-friendly, low-literacy user base). The remaining 9 findings were all false positives against deliberately correct ARIA patterns already in the codebase (see below) and were suppressed per-file with scoped `.oxlintrc.json` overrides, not a blanket plugin-wide disable. A manual code-level audit (the interactive keyboard/screen-reader pass from the spec wasn't possible — see Browser check) found one real issue: the `pass`/`caution` status-badge color tokens (`--pass`, `--caution` in `src/index.css`) fell just under the WCAG AA 4.5:1 text-contrast threshold against their `-soft` background pairs (measured 4.4 and 3.98). Both were darkened by a barely-perceptible amount (`#1b7f4b`→`#1b7d4a`, `#a86a00`→`#9b6200`) to clear 4.5:1, and the same values were mirrored into `PartnersMap.tsx`'s duplicated marker-color constant so the two sources of truth don't drift.

Dynamic `<html lang>` (planned as new work) turned out to **already exist**: `SessionProvider.tsx` already calls `setDocumentLanguage(language)` in a `useEffect` keyed on the session's language state, which sets `document.documentElement.lang`. Verified rather than rebuilt.

## Design decisions (confirmed with the user before writing the spec)

1. PWA scope is installable + static-asset caching only — no offline mutation queueing/background sync, which would be a much larger separate feature.
2. A11y enforcement is oxlint's `jsx-a11y` (built in, no new dependency) plus a manual audit and fixes — no `vitest-axe`/`jest-axe` test dependency added this phase.

## A false-positive triage worth recording

Three ARIA-pattern implementations tripped `jsx-a11y` rules that don't understand their patterns:
- `states.tsx`'s `LoadingBlock`, `VerifyScreen.tsx`'s result card: `role="status"` on a `<div>` for an `aria-live` announcement region — `prefer-tag-over-role` suggested `<output>`, which has different (form-result) semantics and isn't the idiomatic pattern for a loading/status live region. Suppressed `jsx-a11y/prefer-tag-over-role` for these two files.
- `MoneyBar.tsx`: `role="img"` on a `<div>` composed from multiple child divs (a stacked money bar) with `aria-label` giving the flattened summary — the standard way to make a non-`<img>`-representable visual composition accessible as a single unit. Same rule, same suppression.
- `DistrictSearch.tsx`: a full `aria-activedescendant`-based combobox (`role="combobox"`/`listbox`/`option`) — the WAI-ARIA APG-recommended pattern for a custom searchable autocomplete that a native `<select>` can't do (fuzzy district-name matching). `prefer-tag-over-role`, `no-noninteractive-element-to-interactive-role`, and `click-events-have-key-events` all false-positive against it, since keyboard interaction is intentionally centralized on the `<input>` (arrow keys/Enter), not on the non-focusable `<li>` options. Suppressed all three, scoped to this one file.
